## 2026-09-22 — M1 gate passed: scanner reaches 100% recall, 100% precision on the fixture

Built `packages/scanner` (`index-ds.ts`, `fingerprint.ts`, `extract.ts`, `shortlist.ts`) exactly
per CLAUDE.md §5.1-§5.3: ts-morph AST work only, zero network, zero model calls. Golden test
(`packages/scanner/test/precision.test.ts`) runs it against `fixtures/drift-demo/EXPECTED.json`.

Measured result: **68 raw candidates extracted, 18 shortlisted, all 18 correspond to a planted
case** (12 true drifts + 3 negatives-adjacent + 3 traps, matching `EXPECTED.json`'s 18 cases) —
**100% recall, 100% precision, 0 false positives, 0 flagged negatives** against the M1 gate's
minimum of 100% recall / 80% precision. 50 raw candidates were filtered before reaching a
shortlist (the "filtered before inference" number that will anchor the cost panel in §7).

Two rule refinements were needed beyond CLAUDE.md §5.3's literal table, both recorded here since
they're not obvious from the spec text alone:

1. **Card rule drops the "containing a heading" qualifier.** `trap-002` (a layout `div` carrying
   every Card class token but no grouping semantics) has no literal heading child — it just wraps
   `{children}`. Per its own case description ("the shortlist rules *will* surface it"), the
   heading check can't be a hard gate at the shortlist stage; semantic rejection is an M2
   (adjudicator) job. Card shortlist = `rounded-* + border + p[xy]?-*` on a div/section/article,
   full stop.
2. **Button rule needed a "button-shaped `<a>`" case.** `trap-001` is a marketing CTA `<a>` styled
   as a pill button (`inline-flex` + `rounded-full` + `px-10`) with no click handler — the
   original table's "handler + cursor-pointer" signal doesn't fire on a real link. Added:
   `rootTag === "a"` + `inline-flex` + `rounded-*` + `px-*` → Button.

**One extraction-level exception, not in the spec's rule table:** a `fixed inset-0 z-*`
dialog/overlay root is extracted as a single atomic candidate and its children are *not* walked
for further candidates. Without this, the modal's backdrop div and its rounded/bordered/padded
content wrapper (which — coincidentally — structurally matches the Card rule, since it contains an
`<h2>`) would surface as spurious extra candidates nested inside a case that's already correctly
identified as Dialog. A dialog's internal structure is an implementation detail of the dialog, not
a separately-owned candidate. Implemented once in `shortlist.ts` (`isDialogOverlay`) and reused by
`extract.ts` for the recursion cutoff, so the predicate can't drift out of sync between the two
call sites.

## 2026-09-22 — Post-hackathon: multi-provider routing and standalone package, deferred on purpose

Two questions came up about life after the submission deadline: can Doppel route to other LLM
APIs (Claude, ChatGPT) besides Nebius/Nemotron, and can any part of it be published as a
standalone package. Both are "yes, and the current design already leans that way" — but neither
should be built now, and here's why, so a future session doesn't second-guess the M1-only scope.

**Multi-provider routing.** CLAUDE.md §0.4's single-choke-point rule (every LLM call goes through
`packages/agent/src/route.ts`) is exactly the right seam for this — it's just not built yet (M2).
When it is, `route()` should be keyed by an abstract tier (`nano`/`super`/`ultra`) mapped to a
`{provider, model}` pair in config, never a hardcoded Nebius model ID inlined at call sites (which
§3.1 already mandates for a different reason — pinning from `GET /v1/models`). Under that design,
adding OpenAI is a same-SDK baseURL swap (Nebius's inference API is already OpenAI-compatible per
§3.1). Adding Claude needs a thin adapter behind the same `route()` signature, since Anthropic's
native API isn't OpenAI-shaped. **Not doing this now**: building a provider-abstraction layer
before `route.ts` itself exists is scope CLAUDE.md's own non-goals (§12) and risk list (§11.5,
"ship in milestone order") would flag — M2 hasn't started because `NEBIUS_API_KEY` hasn't landed.
Revisit when `packages/agent` is actually being built.

**Standalone package.** `packages/scanner` is already the most publishable piece of the project —
zero network, zero model dependency (CLAUDE.md §5.2/§15: "no network dependency and no model
dependency"), works entirely on its own. Post-hackathon it's a reasonable candidate for its own
npm package: a CLI/library that finds hand-rolled design-system components with no Nebius account
or API key required at all. Two things stand in the way today: it's `workspace:*`-linked to
`@doppel/shared` (fine inside this monorepo, not fine published standalone), and its shortlist
rules in `shortlist.ts` hardcode shadcn/ui conventions (`cva`, `rounded-*`/`border`/`p-*` token
shapes) rather than taking them as config. **Not doing this now**: decoupling and generalizing it
mid-hackathon risks the M1 gate's own precision numbers (CLAUDE.md §11.5 — "a defensible 84% reads
as engineering maturity" only if the numbers stay measured against a stable implementation).
Revisit after M5 ships.

**New finding, not in §17's list: these are reasoning models, and that has real cost/prompt
consequences.** All four completions came back with non-null `completion_tokens_details.
reasoning_tokens`. With the spike's 20-token `max_tokens` budget:

- Nano and Super both returned **`content: null`** — they spent the entire budget on internal
  reasoning and never emitted the requested one-word answer. The response is a well-formed 200,
  `usage.completion_tokens: 20`, `reason: null` — nothing distinguishes "ran out of budget mid-
  thought" from "chose to say nothing" without inspecting `reasoning_tokens` specifically.
  Silently treating `content` as the answer (e.g. a naive `res.choices[0].message.content` in
  `route.ts`) would look like the model returned an empty string, not that it needed a bigger
  budget.
- Ultra answered `"pong"` correctly, but only because it needed just 14 of the 20 reasoning tokens
  first.
- Reasoning tokens are billed as ordinary completion tokens (`completion_tokens` includes them,
  there's no separate reasoning-token price tier visible in the response). This is directly
  relevant to §7's cost panel and to the "route Nano/Super over Ultra to save credits" pitch — a
  Nano call that reasons for 500 tokens before a 10-token answer can cost more than expected, and
  the counterfactual-savings math in §7 needs to account for reasoning tokens, not just the
  requested completion length.

**Action items before writing `packages/agent/src/route.ts` (M2):**
1. Every structured-output prompt needs a `max_tokens` budget generous enough to cover reasoning
   *and* the answer — not sized to the answer alone. Needs empirical tuning per stage once real
   triage/adjudicate/migrate prompts exist.
2. Check whether the Nebius/Nemotron API exposes a way to cap or disable reasoning (an
   `reasoning_effort`-style param, if OpenAI-compatible reasoning controls are supported) — worth
   one more spike call before assuming max_tokens-padding is the only lever.
3. `route.ts`'s usage logging (CLAUDE.md §6, `llm_calls` table) must capture `reasoning_tokens`
   separately from the visible answer, not just total `completion_tokens`, or the cost panel will
   be accurate in total spend but misleading about why.

Drafted as a `docs/FEEDBACK.md` entry too — reasoning-token opacity with no distinguishing signal
for "still thinking" vs. "nothing to say" is genuinely useful, specific feedback for Nebius/NVIDIA.

## 2026-09-23 — M2 built: packages/agent, router, and the full triage→adjudicate→migrate loop

Built `packages/agent` in full per CLAUDE.md §5.4-§5.7: `route.ts` (the single choke-point router,
§0.4), `schemas.ts` (zod for every structured output), `prompts/*.md` (versioned, loaded at
runtime), `triage.ts`/`adjudicate.ts`/`migrate.ts`/`repair.ts`/`ds-describe.ts`, `usage-log.ts`
(JSONL sink — see the M4/DATABASE_URL note below), `pricing.ts`. Unit-tested `route.ts`'s retry
contract against a mocked client (`test/route.test.ts`, 5 tests, zero network cost): valid response,
null-content retry, schema-invalid retry, hard failure after 2 attempts, and that every attempt
logs a usage row.

Built `scripts/m2-pipeline.ts` to actually prove the pipeline end-to-end against
`fixtures/drift-demo` with real API calls, applying patches via ts-morph and checking real
`tsc --noEmit` diagnostics — not a mock. This is where the real engineering happened; 9 live runs
against the fixture, each one surfacing a genuine bug or a genuine dead end. Recorded in full
because the failure/fix history is more useful than a clean summary would be.

**Real bugs found and fixed, in the order discovered:**

1. **`Node.replaceWithText()` is unreliable for JSX.** ts-morph's node-level replace does an
   incremental AST tree-diff between old and new content, and throws ("Error replacing tree!
   Perhaps a syntax error was inserted") on perfectly valid replacements whenever the old/new
   shapes don't line up node-for-node — common for JSX. Fixed by switching to
   `sourceFile.replaceText([node.getStart(), node.getEnd()], text)`, which is a straight
   splice+reparse instead of tree reconciliation, while still deriving the range from the real AST
   node (not a guessed offset) — still "ts-morph node replacement," per CLAUDE.md §5.6, just via a
   more robust primitive.
2. **String-based import dedup missed real duplicates.** Comparing `getText()` strings caught
   exact-text matches only; a model writing `import { Button } from '@/components/ui/button'`
   (single quotes) against a file already importing the same thing with double quotes produced a
   literal duplicate import → `Duplicate identifier 'Button'`. Fixed by routing all import handling
   through ts-morph's own `addImportDeclaration`/`addNamedImport` API, which compares semantically
   (module specifier + name), not by text.
3. **Sub-component imports (`DialogContent`, `TableHeader`, ...) got dropped even after
   strengthening the prompt.** Trusting the model's `importsToAdd` for every sub-component wasn't
   reliable enough. Fixed deterministically instead: regex-scan the actual `replacementJsx` for
   every capitalized JSX tag it uses, and for each one that matches a known DS component (from the
   already-loaded DS index), guarantee its import via the semantic API above — regardless of what
   the model's `importsToAdd` says. The model is still trusted for genuinely external imports
   (icons, utilities) it's the only source of truth for.
4. **A string can be valid JSON and still be broken JSX.** The most persistent failure: models
   would return well-formed JSON where `replacementJsx` was truncated mid-element (observed
   directly via an isolated debug call: the raw value was literally `"<Alert variant="`, 15
   characters, cut off before the closing quote of a variant name). zod's `z.string().min(1)`
   happily accepts that. Splicing it into the real file produced confusing cascading diagnostics
   far from the actual defect (`Identifier expected` dozens of lines past the patch site — the
   parser recovering from an unclosed tag). Fixed with a pre-splice gate (`findJsxSyntaxError` in
   `scripts/m2-pipeline.ts`): wrap the fragment in a throwaway component, parse it with an
   in-memory ts-morph `Project` (`jsx: Preserve` — `ReactJSX` needs to resolve `react/jsx-runtime`
   types, which an in-memory project with no `node_modules` can't do), and check for genuine
   parse/structure error codes via an **allowlist** (1003, 1005, 1109, 1128, 1136, 1145, 1160,
   1161, 1381, 1382, 17002, 17008, 2657) rather than a blocklist of resolution errors — "cannot
   find name" has multiple code variants (2304, 2552, 2663, ...) depending on phrasing, and
   blocklisting them one at a time is a losing game.
5. **`maxTokens` tuning: tested and mostly ruled out as the cause.** Raised `migrate`/`repair` from
   6000 to 16000 to test the "reasoning eats the budget" theory from the day-one spike. Result was
   clarifying, not fixing: one failure's truncation position scaled up proportionally (~5500 →
   ~15500 characters), proving that specific case is a genuine runaway-repetition loop, not a
   budget shortfall — more headroom just let it fail later, at higher cost. The recurring "L4:
   '{' or JSX element expected" failures happened at nearly the same rate at 16000 as at 6000,
   ruling out budget as their cause too. Settled on 8000 as modest, cheap insurance — not the fix.
6. **`strict: true` didn't fix the truncation either, and that result was itself informative.**
   Hypothesis: `strict: false` in the `response_format.json_schema` request meant the API wasn't
   doing real grammar-constrained decoding, so the model could emit an unescaped `"` inside a JSX
   attribute (e.g. `variant="destructive"`) that would prematurely terminate the JSON string.
   Tested `strict: true` in isolation against the exact candidate that reliably failed — the API
   accepted it (no schema-incompatibility rejection, despite `zod-to-json-schema`'s output not
   setting `additionalProperties: false`), but the output was **identical**: `"<Alert variant="`.
   This proves the JSON is syntactically valid the whole time — grammar constraints were never the
   problem. The model is choosing to close the string and move on with genuinely incomplete
   content; no amount of JSON-grammar enforcement can fix a semantically-wrong-but-syntactically-
   valid string value. Kept `strict: true` anyway (no observed downside, plausibly helps schema
   conformance generally) but it is **not** the fix for this failure mode. Worth flagging to
   Nebius/NVIDIA — logged in `docs/FEEDBACK.md`.
7. **A few-shot example in the prompt made things measurably worse (3/10 vs. a prior best of
   9/10), not better.** Added one JSON-encoded example of a correct multi-child migration to both
   `migrate.md` and `repair.md`, on the reasoning that the recurring failures cluster specifically
   on multi-child JSX (Alert/Card/Dialog/Table) while flat single-element migrations (Button)
   succeed reliably — a textbook case for few-shot guidance. Measured result was a regression: the
   failure mode shifted back toward malformed-JSON-at-position-~6000-7700 (the same signature as
   the pre-strict-mode failures), and only 3/10 patches passed, the worst run recorded. Best guess:
   embedding a pre-escaped JSON blob inside a JSON-schema-constrained prompt made the prompt
   heavier and pushed more calls into the reasoning-budget-exhaustion zone rather than clarifying
   the target shape. **Reverted.** Recorded here specifically so a future session doesn't re-try
   the same fix expecting a different result.

8. **Root cause found and fixed: single vs. double quotes in JSX attribute values.** Every
   truncation signature above (`"<Alert variant="` cut off exactly before the value that would need
   an escaped quote; malformed-JSON positions clustering wherever a quote-heavy migration happened
   to land) pointed at the same mechanism: `replacementJsx` is itself a JSON string, and standard
   JSX style (`variant="destructive"`) requires the model to emit `\"` mid-string to represent it.
   The model was inconsistent at that specific escaping task, and inconsistent in a way neither
   `strict: true` nor more `max_tokens` could fix (both already ruled out as causes above — the
   JSON was syntactically valid the whole time, just short). Instructed `migrate.md`/`repair.md` to
   use single quotes for JSX attribute string values instead (`variant='destructive'`) — a JSON
   string never needs to escape `'`, so the failure mode is structurally impossible once the model
   follows the instruction. Verified cheaply before a full run: 3 isolated calls on the
   single-worst-performing candidate (Alert, historically failing on 4 of the last 5 runs) came
   back clean 3/3, and 4 isolated calls on the two most complex candidates (Table with 6
   sub-components, Dialog) came back clean 4/4 — 7/7 total, at the cost of a handful of Ultra calls
   instead of a full ~40-call pipeline run.

**Result: M2 gate cleared.** Full pipeline re-run with the fix: **15/15 DRIFT-classified candidates
passed `tsc --noEmit` on the first attempt — zero repairs needed, zero pre-splice errors.** (18
shortlisted → 18/18 survived triage → 15 DRIFT / 2 `INTENTIONAL_DEVIATION` / 1 `NOT_DRIFT`, all
correctly classified per `EXPECTED.json`.) Against the gate's target of ≥10, this is comfortably
clear. Quote style makes no difference to how the code runs or typechecks — this was purely an
LLM-structured-output encoding issue, not a real constraint on the generated code, and downstream
Prettier formatting (§5.6) will normalize quote style to the repo's convention regardless. Logged
as its own `docs/FEEDBACK.md` entry — this is a specific, actionable, non-obvious finding about a
real limitation of JSON-schema-constrained decoding for code-generation tasks.

Classification-accuracy side note: the adjudicate prompt was independently strengthened mid-session
(explicit guidance that "has a variant/color the DS component doesn't support" is DRIFT with
`unmappable`, not `INTENTIONAL_DEVIATION`) after observing real misclassifications — a gradient CTA
and a `role`-less alert both got wrongly called `INTENTIONAL_DEVIATION` before the fix, and
`components/layout/shell.tsx` (trap-002) went from wrongly `INTENTIONAL_DEVIATION` to correctly
`NOT_DRIFT` after. This is a real, measured improvement, independent of the migrate-stage gate
discussion above.

## 2026-09-23 — Started M3: packages/verifier's sandbox-independent pieces

Sandboxes beta access is requested but not yet granted (this account's `whoami` still returns
zero permissions). Per the same logic as M1 (§11.1 — build what doesn't need the blocked
dependency first), built the parts of `packages/verifier` that don't need a live sandbox:

- **`diff.ts`** — pixelmatch wrapper, `includeAA: false` set explicitly (this is pixelmatch's
  default and already is the "anti-aliasing tolerance on" behavior §5.7 step 2 asks for; made
  explicit rather than relying on an unstated default). Tested with synthetic PNGs generated via
  `pngjs` directly — no screenshots needed to verify the diff math itself.
- **`verdict.ts`** — the §2.1 decision table as a pure function, reading `DOPPEL_PIXEL_PASS_
  THRESHOLD`/`DOPPEL_PIXEL_REVIEW_THRESHOLD` from env per §16 with matching defaults (0.005/0.05).
  Fully unit-tested including the "worst viewport wins" rule from step 5.
- **`harness.ts`** — generates the isolation render harness (§5.7 step 1). One real design
  decision made here, not explicit in CLAUDE.md: the harness renders ONE component variant per
  generation, not both original-and-patched side by side. §3.3's sandbox strategy already forks a
  new instance per patch from a warm base image — so "renders it twice" reads more naturally as
  "the orchestrator runs this same harness twice, against two different sandbox states" than as
  "one harness juggles two component versions." This avoids a real mess (duplicate module
  resolution, picking a variant via runtime query param when ES imports are static) for no benefit.
  Providers (ThemeProvider, a memory router, a mock query client) are caller-supplied snippets, not
  hardcoded to a specific library, since this package has no way to know what a given target repo
  uses. Verified the generated TSX is real, parseable code — not just plausible-looking strings —
  by reusing the same allowlist-based structural-error check from `scripts/m2-pipeline.ts`
  (`findStructuralErrors` in `test/harness.test.ts`), including a test that provider nesting closes
  in the correct reverse order.
- **`sandbox.ts`** — written as a stub, explicitly and repeatedly marked as such in its own file
  header. `whoami()` is real (confirmed live in the day-one spike); `spawnInstance()` follows the
  documented request shape but has never been exercised against a real response, since this
  account's `spawn` permission is still `false`. Re-run `pnpm spike` once access is granted — it
  already calls the same endpoints and will surface any shape mismatch immediately, before
  `spawnInstance` gets trusted for real orchestration.

## 2026-09-24 — M3 (verify) wired into the live orchestrator

`apps/web/lib/pipeline.ts` previously persisted every DRIFT finding with `verdict: null`
("not yet verified") — packages/verifier existed and had its own passing gate (`scripts/
m3-pipeline.ts`, one hardcoded candidate), but nothing called it from a real run. That gap is
closed.

**The real architectural piece, done properly rather than skipped:** CLAUDE.md §3.3 requires
"fork per patch from a warm base" — one `npm install`/Playwright-install per RUN, not per
candidate, because paying that cost per candidate is explicitly called out as "far too slow —
you'd burn the whole verification budget on npm." The existing `runVerification` (from the M3
gate) did setup once, but ONLY for a single candidate — calling it once per finding in a live run
would violate §3.3 outright. Fixed by splitting `packages/verifier/src/verify.ts`'s internals into
`verifyFromWarmImage` (forks a caller-supplied warm image, no setup call) with `runVerification`
now just that plus a one-off setup call — same public API for `scripts/m3-pipeline.ts`, but the
core logic is reusable across many candidates. `apps/web/lib/verify-run.ts`'s `RunVerifier` class
builds ONE warm image per run (memoized on first use) and every candidate forks it.

**Isolation strategy:** rather than rendering the candidate's whole containing file (which may need
router/auth/data context this orchestrator has no way to synthesize), each candidate's own
extracted JSX (before) and migrated JSX (after) is wrapped standalone as `export default function
HarnessTarget() { return (...) }` — sidesteps needing props-synthesis for entire pages. Cost: a
candidate whose JSX references its enclosing scope (a local handler, mapped list item, component
state) won't compile standalone. This isn't patched around — it correctly surfaces as
`UNVERIFIABLE` per §5.7 step 1's "if it still won't mount → stop here, do not guess," which is the
DESIGN, not a bug.

**Real typecheck, not another hardcoded `true`:** `scripts/m3-pipeline.ts` hardcoded
`typecheckPassed: true` ("already proven by scripts/m2-pipeline.ts for this exact migration") since
it only ever verified one pre-validated case. The orchestrator verifies whatever the model just
generated, so that shortcut doesn't hold — `pipeline.ts` now runs a REAL in-memory `tsc --noEmit`
against the exact wrapper content that gets rendered (via ts-morph's `createSourceFile`, never
written to disk, removed after), reusing the run's own `Project` so `@/*` path aliases resolve
against real DS component files. `lintPassed: true` stays hardcoded — still no ESLint config in the
fixture, still not a real signal either way, same honest cut as before.

**Images:** `findings.beforeUrl`/`afterUrl`/`diffUrl` are `text` columns with no blob storage
behind them (none exists — not in CLAUDE.md's architecture, not built for this hackathon's scope).
Storing `data:image/png;base64,...` URLs directly works fine for a plain `<img src>` and needed zero
new infrastructure; documented as the deliberate choice it is, not an oversight. One representative
viewport (768px) is stored per finding — the schema has one slot each, not one per viewport.

## 2026-09-24 — M4: drift map

§9's last unbuilt run-view piece: "Drift map — files as a treemap sized by LOC, coloured by drift

negligible at this scale, and the simpler version is much easier to verify correct. Named "drift
map" (the spec's own term), not claiming to be a rigorous treemap.

## 2026-09-25 — Live demo run failed on Vercel: the documented un-awaited-background-work limitation, for real

The user clicked "Start demo run" on the deployed dashboard and got `status: "failed"` almost
immediately — no useful error surfaced, just the generic "check the server logs" message. This is
exactly the limitation `apps/web/app/api/runs/route.ts`'s own header comment already named before
today: `POST /api/runs` fires `executeRun(...)` without awaiting it, which works fine on a
long-lived process (`next dev`/`next start`, this project's own local testing all session) but has
no guarantee on Vercel, where the platform can freeze or tear down a serverless function once its
response is sent — cutting the in-flight pipeline off mid-run, which surfaces as a real thrown
error inside `pipeline.ts`'s own try/catch (correctly setting `status: "failed"`), not a hang.

**Fixed with Next.js's own API for exactly this**, not a workaround: `after()` (from `next/server`)
schedules work to run after the response is sent, and on Vercel it's wired to the platform's
`waitUntil`, which keeps the function alive for that work instead of tearing it down. Replaced the
bare `executeRun(run, input).catch(...)` with `after(() => executeRun(run, input).catch(...))`.
Also added `export const maxDuration` to both `/api/runs` (300s — a live run's slowest part, M3
verify, can take several minutes) and `/api/runs/[runId]/pr` (60s — properly awaited already, no
cutoff risk, but several sequential GitHub API calls could exceed a short default). Deliberately did
NOT guess a number near Vercel's actual platform ceiling (some evidence suggests exceeding your
plan's real maximum fails the deploy BUILD, not just the runtime) — picked conservative values and
said so in both files' comments, rather than asserting Vercel account-tier specifics this codebase
has no way to actually confirm.

**Still an open, honestly-stated limitation, not fully solved:** `after()` raises the ceiling, it
doesn't remove it — a real run against a repo with many DRIFT candidates going through live M3
verify can still exceed even a generous `maxDuration`. The correct long-term answer, unchanged from
what `pipeline.ts` and this route already said before today, is a real background-job queue
(CLAUDE.md §3.4's Serverless Jobs, or a Postgres-backed job table + poller) that doesn't tie pipeline
execution to any single HTTP request's lifetime at all. Not built here — a real, well-scoped
increment for later, not required to unblock the immediate "a demo run failed" report. Verified
locally before pushing (the one thing that IS fully checkable without another live Vercel deploy
cycle): a fresh local run still starts and produces real LLM call rows correctly with `after()` in
place, no regression from the previous bare-un-awaited behavior.

**That fix alone wasn't enough — tested live against the real Vercel deployment, not assumed.**
A real triggered run on `doppel-web-eight.vercel.app` after deploying the `after()` fix still failed

work. Same root cause as the `config/pricing.json` bug from earlier today, a second instance of it:
